# Agent Notes

Guidance for AI coding assistants (Claude Code, opencode, Copilot, Cursor, etc.) working in this repo.

## What this repo is

**Whimsical Writer** — an AI-powered writing assistant web app. Users can create documents, write with AI assistance (grammar checking, rewriting, summarization, prologue generation, persistent chat conversations), build fictional worlds with character/place/item profiles, track word count goals, save version snapshots, and export to PDF/DOCX.

## Repo layout

- `Writer-Assistant/` — The full application (pnpm monorepo).
  - `artifacts/writer/` — Vite + React frontend (port 8080).
  - `artifacts/api-server/` — Express 5 API backend (port 5000).
  - `artifacts/mockup-sandbox/` — UI component sandbox for previewing shadcn/ui components.
  - `lib/db/` — Drizzle ORM + PostgreSQL schema.
  - `lib/api-client-react/` — Auto-generated (Orval) React Query hooks for the API.
  - `lib/api-spec/` — OpenAPI spec and Orval config.
  - `lib/api-zod/` — Generated Zod schemas from the OpenAPI spec.
- `.devcontainer/` — Codespaces / dev container config (prebuilt Node 24 image).
- `.opencode/skills/` — opencode skill packs (frontend-design, vercel-infrastructure, c4-diagrams).
- `opencode.json` — opencode configuration (model: `opencode/deepseek-v4-flash-free`).

## How to run

All commands run from `Writer-Assistant/`:

```bash
# Push DB schema to Neon (remote PostgreSQL)
pnpm --filter @workspace/db run push

# API server (requires DATABASE_URL and OPENROUTER_API_KEY)
PORT=5000 NODE_ENV=development \
  DATABASE_URL="postgresql://..." \
  OPENROUTER_API_KEY="<key>" pnpm --filter @workspace/api-server run dev

# Or load both from .env:
export $(grep -v '^#' Writer-Assistant/.env | xargs) && \
  PORT=5000 NODE_ENV=development pnpm --filter @workspace/api-server run dev

# Frontend dev server
PORT=8080 BASE_PATH=/ pnpm --filter @workspace/writer run dev

# Typecheck everything
pnpm run typecheck
```

### Database

The app uses **Neon (remote PostgreSQL)**. The connection string is stored in `Writer-Assistant/.env` (gitignored). The app does **not** auto-load `.env` files — you must pass `DATABASE_URL` in the command or export it:

```bash
export DATABASE_URL=$(grep DATABASE_URL Writer-Assistant/.env | cut -d= -f2-)
```

Or inline:
```bash
DATABASE_URL="postgresql://..." pnpm --filter @workspace/api-server run dev
```

For convenience, you can export both env vars from `.env`:
```bash
export $(grep -v '^#' Writer-Assistant/.env | xargs) && PORT=5000 NODE_ENV=development pnpm --filter @workspace/api-server run dev
```

Both servers must run in the background (use `nohup ... &`, `run_in_background: true`, or `tmux new-session -d -s <name> '<command>'`). The `tmux` approach is more reliable in shell environments where nohup'd children get killed when the parent shell exits.

## Security

- **All secrets come from environment variables — never hardcode them.** Every API key, DB connection string, and Clerk secret is read via `process.env.*` (server) or `import.meta.env.VITE_*` (browser-only, publishable values). The only file that ever holds real secret *values* is the gitignored `.env` / `Writer-Assistant/.env`.
- **`.env.example` is the canonical list of required env vars.** It documents every key with a blank placeholder and a production deployment checklist. Copy it to `.env` for local dev. Only `.env.example` is committed; all real `.env*` files are gitignored.
- **`.gitignore` blocks all credential material.** It covers `.env`, `.env.local`, `.env.production`, `.env.vercel`, `.env.*` (with a `!.env.example` exception), plus key files (`*.pem`, `*.key`, `id_rsa`, `id_ed25519`, `.netrc`, `secrets.*`, `credentials.*`, `*.ppk`). Verified via `git check-ignore`.
- **Secrets were never committed to git history.** Confirmed with `git log --all -S "<each-secret-value>"` — the `.env` files were always gitignored.
- **No client-side secret exposure.** The frontend makes **zero** direct calls to AI providers (OpenAI/Groq/OpenRouter/Gemini/etc.) or the database. All such traffic is proxied through `/api/*`, so private keys stay server-side. The only browser-exposed value is `VITE_CLERK_PUBLISHABLE_KEY`, which is designed to be public.
- **`start-dev.sh` sources `.env` instead of hardcoding keys.** The dev-server script loads `Writer-Assistant/.env` (via `set -a; . ./.env; set +a`) rather than baking in a publishable key. If `VITE_CLERK_PUBLISHABLE_KEY` is unset it falls back to guest-only mode.
- **Input validation everywhere.** Every API route validates request bodies and params with Zod `safeParse` (returns generic `400 { error: "Invalid input" }`). AI endpoints additionally cap input size with `.slice()` (suggest 8K–12K, grammar 20K, chat doc-context 16K, summarize 8K, prologue 6K, entity-scan 100K) to prevent context-window overflow and crashes on huge text.
- **Error responses never leak internals.** All `catch` blocks return generic messages (`"Internal server error"`, `"AI rate limit reached. Please try again later."`, `"Image generation failed"`). Full errors are logged server-side only (`logger.error(err)`). The Express error handler (`app.ts`) returns `500 { error: "Internal server error" }`.
- **No SQL injection surface.** All DB access is via Drizzle ORM parameterized queries — there is no raw string-interpolated SQL anywhere.
- **File uploads are magic-byte sniffed.** `upload.ts` uses `fileTypeFromBuffer()` to validate actual bytes (not the client-supplied `Content-Type`), enforces a 10 MB limit, and rejects SVG (XSS vector as a data: URI). Allowed: png/jpeg/gif/webp.
- **Security headers + CSP via Helmet.** `app.ts` configures Helmet with a tuned CSP (self for scripts/styles, allows Clerk origins and the AI connect-src origins). `trust proxy` is set to `1` for Vercel's single hop.
- **CORS is allowlisted.** `isOriginAllowed()` permits same-origin (production domain + every Vercel preview URL via host match), explicitly listed `ALLOWED_ORIGINS`, and localhost in dev. Unknown origins get no CORS headers (browser blocks the response).
- **Guest cookie is HMAC-signed with `GUEST_ID_SECRET`.** Set `GUEST_ID_SECRET` (e.g. `openssl rand -hex 32`) in production so the signed `wa_guest` cookie survives server restarts; if unset, a random secret is generated per start (invalidating guest cookies on redeploy).

## Conventions when editing

- **Sign-in is opt-in; guest mode is the default.** `/sign-in` and `/sign-up` host Clerk `<SignIn>`/`<SignUp>` (`App.tsx`), gated on `VITE_CLERK_PUBLISHABLE_KEY`. A "Continue as guest" link is always available, and when no publishable key is configured the auth pages show a guest-only CTA instead of an empty Clerk form. Guests are identified by a random UUID stored in `localStorage` and sent as the `x-guest-id` header; guest documents persist as long as the browser/localStorage isn't cleared.
- **Identity never returns 401.** The `requireIdentity` middleware in `identity.ts` always passes. If no explicit identity is found (Clerk, guest cookie, or `x-guest-id` header), a fallback is generated from the request IP. This prevents the "could not load documents" error on any deployment.
- **`wa_guest` signed cookie is the primary guest identity; `x-guest-id` is the fallback.** `resolveIdentity` (`identity.ts`) prefers the server-signed `wa_guest` cookie (HMAC-verified — survives localStorage clears), then the `x-guest-id` header (from `localStorage` via `guest-id.ts`, validated as a UUID), then a fresh server-generated UUID. The frontend `guest-id.ts` generates a UUID on first visit, stores it in `localStorage`, and appends `x-guest-id` to every `/api/` request; the server also issues the signed `wa_guest` cookie for that UUID so identity survives JS crashes. No `POST /api/auth/guest` call is needed.
- **Clerk auth is optional and auto-detects.** `app.ts` mounts `clerkMiddleware` only when `CLERK_SECRET_KEY` is set; otherwise it runs guest-only and **logs a warning in production instead of throwing** (so unconfigured deploys keep serving). Resolution order: Clerk user → signed `wa_guest` cookie → `x-guest-id` header → random UUID. `getUserId()` fails closed to `anon:<ip>` if identity is somehow missing. NOTE: the Clerk instance itself (`enabling-reptile-30`) must have at least one sign-in factor enabled (Email/Password, OAuth) in the Clerk dashboard — otherwise `<SignIn>` renders an empty form. The local `.env` has no `CLERK_SECRET_KEY`, so local dev is guest-only.
- **`@clerk/express` v2: `req.auth` is an async function, not an object.** In v2.x (`@clerk/express@^2.1.23`), `req.auth` must be called and awaited: `const auth = typeof req.auth === 'function' ? await req.auth() : req.auth;` then read `auth.userId`. Accessing `req.auth.userId` directly silently returns `undefined` (functions don't have properties), which makes every request fall back to guest identity — Clerk auth appears "configured" but never actually authenticates. This is handled in `resolveIdentity` (`identity.ts`) and the claim endpoint (`auth.ts`). If you add any new route that checks Clerk auth, use the same `await req.auth()` pattern.
- **Cross-device sync via `POST /api/auth/claim-documents`.** Documents created in guest mode are stored under the per-device guest UUID. When a user signs in with Clerk, those documents must be migrated to their Clerk user ID so they appear on all devices. The `POST /api/auth/claim-documents` endpoint (`auth.ts`) reads the Clerk user ID from `await req.auth()` and the guest UUID from the `x-guest-id` header, then in a single DB transaction reassigns all rows in `documents`, `document_versions`, `world_entities`, and `conversations` from the guest UUID to the Clerk user ID. It also clears the `wa_guest` cookie. The endpoint requires Clerk auth (returns 401 otherwise) and is idempotent (returns `{ claimed: 0 }` if no rows match).
- **Claim is triggered from the frontend `ClaimDocumentsEffect` component** (`documents.tsx`), which is only mounted when `clerkEnabled` is true (so `useAuth()` is always inside `ClerkProvider`). It uses `useAuth().isSignedIn` reactively — the effect fires when `isSignedIn` flips to `true` (after Clerk finishes initializing on the post-sign-in redirect). It calls `useAuth().getToken()` and explicitly attaches the `Authorization: Bearer <token>` header. If `getToken()` returns `null` (JWT not generated yet), it retries up to 6 times with 500ms backoff. On success it calls `clearGuestId()` (from `guest-id.ts`) to remove the guest UUID from `localStorage`, then invalidates the document/stats React Query caches. Users must sign in **once on each device where they created guest documents** for those documents to be claimed into their account.
- **A signed-in user with zero documents gets a recovery banner, not a silent empty dashboard.** A lost session (cookie cleared, different browser) makes Clerk hand out a *new* account, or the app treats the user as a brand-new guest — either way the dashboard renders empty even though the user's work is safe in the DB under their real account. The `SignedInZeroDocsBanner` (`documents.tsx`) renders when `isSignedIn` is true and the document list is empty: an AlertTriangle "Your documents aren't here" banner with the signed-in account ID (the `userId`) and a `signOut()` button so the user can switch to the correct account instead of panicking. It sits inside the empty-state block and only mounts when `clerkEnabled` (so guest-only deployments never see it). This is purely a UX guard — it never touches the DB. If work actually is missing, check identity first (see "Debugging data loss / restoring a deleted document" below).

- **AI provider priority (top wins):** `GROQ_API_KEY` → `GROK_API_KEY` → `DEEPSEEK_API_KEY` → `GEMINI_API_KEY` → `OPENROUTER_API_KEY` (default). Groq routes to `https://api.groq.com/openai/v1` with model `llama-3.3-70b-versatile`. Grok/xAI routes to `https://api.x.ai/v1` with model `grok-2`. The OpenAI SDK is configured with `baseURL` set per-provider. The current `.env` has a working `GROQ_API_KEY` (free tier, 100K tokens/day limit) and an expired `OPENROUTER_API_KEY` (returns 401).
- **Groq free tier has a 12K tokens-per-minute (TPM) limit AND a 100K tokens/day limit.** The TPM limit is the one most commonly hit first — a single chat request with large document context can exceed 12K tokens by itself. Groq returns HTTP **413** (not 429) for TPM violations and 429 for daily-limit violations. Both are now caught by the error handlers in `/suggest`, `/grammar`, and `/chat` (checking `status === 413 || status === 429` and the error message for `"rate_limit"`). When the limit is hit, the route returns HTTP 429 with a friendly message. To remove the limits, upgrade to Groq Dev Tier at https://console.groq.com/settings/billing (pay-per-token) or switch to another provider by removing `GROQ_API_KEY` from Vercel env. 
- **AI provider key currently active: Groq.** The `GROQ_API_KEY` in `.env` and Vercel works for all AI features. The `OPENROUTER_API_KEY` is expired (returns 401) — it's only used as a last-resort fallback if no other provider key is set.
- **All guests get unlimited AI (no paywall).** In `pro-context.tsx`, `isPro` is hardcoded to `useState(true)`, so `useRequest()` always returns `true`. The rate-limit code (3 requests → upgrade modal) is present but inactive. Can be enabled later when sign-in and payment are implemented.
- **Users can supply their own AI API key to use their own provider/quota.** They **do NOT bypass the 10K daily token limit.** The `checkDailyLimit()` call in `resolveAiConfig()` (`ai.ts:292`) runs before any other check — it applies to ALL users including those with custom keys. The `UserApiKeyDialog` (`components/user-api-key-dialog.tsx`) lets a writer paste an OpenAI-compatible key + optional `baseUrl` + `model`, stored in `localStorage` (`wa_user_api_key`, `wa_user_base_url`, `wa_user_model`) via `lib/api-key.ts`. The `guest-id.ts` fetch monkey-patch reads these and attaches them as `x-user-api-key` / `x-user-base-url` / `x-user-model` headers on every `/api/` request; the backend uses those headers in place of the server-side provider keys. A **toggle Switch** in the dialog (and the `wa_user_api_key_enabled` flag, default on) lets the user turn their stored key off without deleting it — when disabled, `guest-id.ts` skips injecting the headers and the documents/editor headers fall back to the free tier badge. The dialog subscribes to the toggle via `useSyncExternalStore` so it reflects cross-tab changes. `hasUserKey` in both `documents.tsx` and `editor.tsx` is `!!getUserApiConfig() && isUserApiKeyEnabled()`.
- **AI token usage is tracked per user/day.** The `ai_usage` table (`lib/db/src/schema/usage.ts`) records `promptTokens`, `completionTokens`, `totalTokens`, and `requests` per `userId`+`date` (unique index). A `trackTokens(userId, completion)` helper in `ai.ts` is called after **every** `chat.completions.create()` call (all endpoints: `/suggest`, `/grammar` scan+fix, `/scan-entities` by-name+bulk, `/generate-prompt` + scanner, `/summarize`, `/prologue`, `/chat`) and upserts the token counts via a **select-then-upsert** pattern (SELECT existing row for today → UPDATE with added tokens, or INSERT if none exists). This replaced an earlier `onConflictDoUpdate` with `EXCLUDED` references that failed silently on Vercel serverless. The function reads `completion.usage` from the OpenAI SDK response (Groq returns `prompt_tokens`, `completion_tokens`, `total_tokens`). The `GET /api/ai/usage` endpoint (`ai.ts`) returns today's totals, a 30-day history, the daily limit (100K for Groq free tier), and the active provider/model name. Token counters appear on the home dashboard (`documents.tsx`, stats grid + My Documents card) **and in the editor header** (`editor.tsx`, next to word count with a Zap icon, auto-refreshing every 15s via `refetchInterval` and immediately after each chat message via `queryClient.invalidateQueries`). The Vite proxy must include `/api/ai` (it already does via the `/api` prefix) so the usage fetch resolves locally.
- **Per-user token limit overrides via `USER_TOKEN_LIMITS` env var.** The default daily AI token cap is `DAILY_LIMIT = 10000` (`ai.ts`). The `USER_TOKEN_LIMITS` env var (JSON map of userId → token limit, e.g. `'{"user_3Elz4gPWW6qOgq4ESVEOzSzRzQY":20000}'`) lets specific users get a higher (or lower) limit without changing the global default. `parseUserLimits()` parses it once at startup; `getEffectiveLimit(userId)` returns the user's override or falls back to `DAILY_LIMIT`. Both `checkDailyLimit()` (enforcement) and `GET /api/ai/usage` (the `dailyLimit` field shown in the editor/dashboard token counter) use the per-user effective limit, so overridden users see their correct limit in the UI and get blocked only when they exceed *their* limit. Set this in Vercel env (production) — it is NOT committed in `.env` (gitignored); only `.env.example` documents it. Note: there is no username field in the DB — overrides are keyed on the raw `user_id` (Clerk ID like `user_...` or guest UUID).
- **AI chat scan mode is the user's choice: active chapter (default) OR the whole manuscript in chunks.** A `chatScanMode` toggle (`"chapter" | "book"`, default `"chapter"`) sits at the top of the chat panel (`editor.tsx`). In **chapter mode** the frontend builds only the active chapter's text via `stripHtml(content)` (live unsaved typing included), the badge reads "Chapter N synced (N words)" (`wordCount`), and a `ChapterPicker` selects which chapter to scan (by switching the editor canvas). If a single chapter alone exceeds `DOC_CONTEXT_CAP`, a `ChunkSelector` (labeled "Section X of Y", scoped to that chapter) picks the section. In **book mode** it builds the FULL book via `stripHtml(rebuildFullContent(content))` — all chapters joined with `\n\n` — and the whole manuscript is chunked at `DOC_CONTEXT_CAP` with a `ChunkSelector` over `bookText`, badge "Manuscript synced (N words)" (`bookWords`). The chosen text is embedded in a system message; the backend (`ai.ts`) merges that system message with the base system prompt into a **single unified system message** before calling the AI. The system prompt adapts to the scan mode: book mode says "Your manuscript titled ... (~N words total across N chapters)", chapter mode says "The user is on chapter N of M, titled ...". `max_tokens` is 1500 for the chat endpoint (same as other AI endpoints). Context is capped at `DOC_CONTEXT_CAP = 16000` characters (~4K tokens) per request to fit within Groq's 12K tokens-per-minute (TPM) free-tier limit — the old value was 90000 but that exceeded the TPM limit and caused 413 errors. The cached `chatDocContent` (a ref) is keyed by `chatDocKeyRef` ("book" vs `chapter:<id>`) so toggling mode or switching chapters drops stale context instead of leaking the previous source's text into the next turn; `setChatChunkIndex(0)` on toggle resets the section. This chat toggle is the exception — grammar, AI Rewrite, Summarize, and Prologue always operate on the active chapter only.
- **AI endpoints cap input size to avoid 500s.** The `/suggest`, `/grammar`, and `/chat` endpoints slice incoming text before sending it to the model: suggest caps at 8K chars (12K for `shorten`), grammar caps at 20K chars (`GRAMMAR_CAP`), and chat's document context is capped at 16K (`DOC_CONTEXT_CAP`). Without these caps, large documents blow past the model's context window and the AI provider returns an error that surfaces as a 500. Summary and prologue already cap at 6K–8K.
- **Chunk selectors let users pick which part of a long doc the AI sees.** When a document exceeds a feature's cap, the chat / grammar / AI Rewrite panels show a reusable `ChunkSelector` component (`editor.tsx`, near the top of the file) with prev/next buttons, "Part X of Y", a first/last text snippet preview, and the exact char range. The snippet (`boundarySnippet`) shows a **short window (~35 chars per side)** centered on the chunk start boundary and the chunk end boundary, snapped to word boundaries, so writers can see exactly where the split happens without reading a full paragraph. Each window is prefixed/suffixed with `…` when there's more text beyond it (e.g. *"…villagers fled as the dragon approached… …she raised her hand and the magic…"*). The preview wraps up to 2 lines via `line-clamp-2`. The selector only renders when `totalChunks > 1`, so short docs see no UI change. Each feature has its own chunk size and its own `*ChunkIndex` state: `chatChunkIndex` (16K chunks — over the WHOLE manuscript, see above), `grammarChunkIndex` (20K), `suggestChunkIndex` (8K). The chat selector's label and text come from `bookText` (whole-manuscript plain text, computed in the same `useMemo` as `bookWords`); grammar and suggest still chunk the active chapter. All three are wired on both desktop and mobile panels.
- **Grammar chunking shifts offsets back to full-text space.** `handleGrammarCheck` slices the selected 20K-char chunk and sends only that to `/api/ai/grammar`. The `grammarStartRef`/`grammarLenRef` maps still cover the FULL plain text (built via `buildPlainTextWithMap`). The AI returns offsets relative to the chunk, so on success each error's `offset` is shifted by `chunkStart = grammarChunkIndex * GRAMMAR_CAP` before `setGrammarErrors`. This keeps `plainSpanToHtml()` (which indexes into the full-text maps) working correctly for inline highlights and Apply.
- **AI Rewrite chunking splices the rewrite into the chunk's HTML range.** `handleSuggest` builds the plain-text→HTML map, slices the selected 8K-char chunk, and stores that chunk's HTML `[start, end)` range in `suggestChunkRef` along with the suggest type. `handleApplySuggestion` then splices the rewrite (wrapped in `<p>` tags via `plainTextToHtml()`) into that range instead of clobbering the whole document — preserving the rest of the doc's formatting. For the `continue` type (which returns only new text, not a rewrite), it inserts AFTER `htmlEnd` rather than replacing. If `suggestChunkRef` is null (no chunk stored, e.g. doc shorter than 8K), Apply falls back to replacing the whole editor content (legacy behavior).
- **Documents are split into chapters.** A document owns an ordered list of chapters in the `chapters` table (`lib/db/src/schema/documents.ts`): `id`, `documentId` (FK cascade), `userId`, `title`, `content` (HTML), `position` (order), `wordCount`, timestamps. The editor edits **one chapter at a time** (`content` state = the active chapter's content), so most AI features (grammar, AI Rewrite, Summarize, Prologue) naturally operate per-chapter instead of over the whole document. **Chat has a scan-mode toggle** — it defaults to the active chapter canvas and can opt into reading the entire manuscript in chunks (see "AI chat scan mode is the user's choice" above). The `Chapter` type and React Query hooks (`useListChapters`, `useCreateChapter`, `useUpdateChapter`, `useDeleteChapter`, `useReorderChapters`) live in `artifacts/writer/src/lib/chapters-api.ts`. Chapter REST routes (`/api/documents/:documentId/chapters`, `/api/documents/:documentId/chapters/reorder`, `/api/chapters/:id`) live in `artifacts/api-server/src/routes/chapters.ts` (mounted in `routes/index.ts`). The Vite proxy has a `/api/chapters` entry (the nested `/documents/.../chapters` paths are already covered by the `/api/documents` prefix).
- **Chapters are lazy-migrated from legacy docs.** Older documents (pre-chapters) store everything in `documents.content`. When such a doc is opened in the editor, the load effect (`editor.tsx`) sees the chapters list is empty and POSTs a single `Chapter 1` seeded with `document.content`, then switches the editor to it — so nothing is lost. `initRef` guards one-time hydration per `documentId`. New chapters are created blank via the "Add Chapter" button and appended at `position = max(existing) + 1`.
- **The editor's `saveContent` persists the active chapter AND keeps `documents.content` in sync.** On every debounced save it (1) PATCHes the active chapter (`/api/chapters/:id` with `{ content }`, only when that chapter's content changed) and (2) PATCHes the parent document with `{ title, content: rebuildFullContent() }` — where `rebuildFullContent()` joins **all** chapters' content with `\n\n`. The document-content sync exists so consumers that still read `documents.content` (dashboard word counts, `GET /api/documents/stats`, world-building entity scans, version snapshots) keep seeing the whole manuscript. `lastSavedRef` tracks `{ title, activeChapterContent }`; it is reset on every chapter switch.
- **Chapter switching flushes the current chapter first.** `switchChapter(id)` calls `flushSave()` (clears the debounce timer + `saveContent`), then loads the target chapter via `applyEditorContent` (imperative `setContent`, since the `RichTextEditor` memo comparator skips the `content` prop), resets `lastSavedRef`/`latestHtmlRef`, and clears grammar errors + chunk indices (`clearChapterGrammarState`). Switching chapters resets the TipTap undo history (the ProseMirror doc is replaced) — undo does not cross chapters.
- **The Chapters (TOC) tab is the first sidebar tab.** It lists chapters (numbered, with per-chapter word counts; the active chapter shows the live editor word count, others show their stored `wordCount`), and supports: switch (click), inline rename (pencil → `<input>`, committed on blur/Enter), move up/down (chevrons → reorder endpoint), delete (trash; blocked when only one chapter remains), and an "Add Blank Chapter" button. All chapter handlers are wrapped in `useRefCallback` (`stableSwitchChapter`, `stableAddChapter`, `stableDeleteChapter`, `stableStartEditTitle`, `stableCommitEditTitle`, `stableMoveChapter`) so the sidebar `useMemo` deps stay stable across keystrokes; chapter state (`chapters`, `activeChapterId`, `editingChapterId`, `editingTitle`, `createChapter.isPending`) is added to both the desktop and mobile sidebar memo dep lists.
- **An "Entire book" word count row sits at the top of the Chapters tab** (desktop + mobile, `editor.tsx`). It sums all chapters' word counts in real time — using the live editor `wordCount` for the active chapter and each chapter's stored `wordCount` for the others (`chapters.reduce((sum, c) => sum + (c.id === activeChapterId ? wordCount : c.wordCount), 0)`). It renders as a bordered muted row between the "Add" button and the chapter list, so writers always see the whole-manuscript total while editing a single chapter.
- **A `ChapterPicker` dropdown sits at the top of the grammar / AI Rewrite / chat panels** (desktop + mobile). It lists chapters and, when changed, calls `switchChapter` (switching the editor too, so grammar highlights / Apply target the visible chapter). It only renders when there's more than one chapter. This is the direct "grammar check for chapter 1 or 2" affordance the chunk selectors used to provide — but now selection is by chapter, and the old "Part X of Y" selectors are scoped **within a single chapter** and relabeled "Section X of Y" (`ChunkSelector`), so they only reappear when one chapter alone exceeds a feature cap.
- **Scroll to the bottom of a chapter to flow into the next one.** The editor scroll container (`editorScrollRef`) listens for `wheel` (desktop) and `touchend` (mobile); when the user is at the very bottom (`scrollTop + clientHeight >= scrollHeight - 8`) and makes another downward gesture, it calls `switchChapter(next)` and resets scroll to the top of the new chapter (double `requestAnimationFrame`, since content swaps synchronously). It deliberately listens to wheel/touchend and **not** the raw `scroll` event so the editor's cursor scroll-into-view while typing never falsely triggers a chapter change. A `chapterAdvanceCooldown` ref (700ms) prevents a single gesture from firing twice. A "Continue to Chapter N ↓" footer button (rendered when a next chapter exists) offers the same action as a click target and makes the gesture discoverable.
- **Version snapshots are per-chapter checkpoints.** Because `content` is the active chapter, `handleSaveVersion` snapshots the active chapter's title+content, and `handleRestoreVersion` restores it into the active chapter — no schema change needed. Summarize/Prologue still operate on the active chapter (effectively the whole doc only if the user keeps everything in one chapter).

- **Grammar check uses AI correction + local LCS diff.** The `POST /api/ai/grammar` endpoint asks the model to return ONLY the corrected text (no JSON, no offset data — the model is unreliable at computing character positions). The system prompt covers 5 categories: spelling, grammar, punctuation, capitalization, and style (for better word choice without cutting text). Temperature is 0.1 to avoid overly conservative output. The backend then runs a local `wordDiff()` function that tokenizes both texts into words, computes a **Longest Common Subsequence (LCS)** table to find edit operations, and maps each diff block to an `errors[]` entry with `message`, `suggestion`, `offset`, `length`, and `type` fields. Error type is determined by `classifyError()` using Levenshtein distance (dist ≤ 2 = spelling, multi-word = style, else grammar). This avoids fragile JSON parsing and accurately handles insertions, deletions, and substitutions.

The heavy work runs in a follow-up task that doesn't count toward INP.
  - **The toolbar format-state sync (`sync()` in `rich-text-editor.tsx`) must bail out when nothing changed.** TipTap's `selectionUpdate` event fires on EVERY keystroke (the cursor moves as you type), and the old code unconditionally built a new `toolbarFmt` object and called `setToolbarFmt(next)` — re-rendering the entire `RichTextEditor` component on every character even though plain typing almost never changes formatting. The updater now does a shallow field-by-field comparison and returns the SAME `prev` reference when all values are identical, so React bails out of the re-render entirely. The toolbar buttons are `memo`-ized so they already skipped, but the parent component function + element tree was still being reconciled per keystroke.
  - **The `darkColorFix` ProseMirror plugin caches its `DecorationSet` by doc reference.** Its `decorations(state)` callback walks every text node via `doc.descendants()` to find dark inline colors to override. Because `decorations()` runs on EVERY transaction (typing AND cursor moves / selection changes), a long document paid a full O(n) walk per keystroke — and since dark mode became the default (commit `4512e7e`), every new user pays this. The decoration set is a pure function of `(doc, isDarkMode)`, so it's memoized by `state.doc` reference in a closure: typing (doc changes) recomputes, but cursor moves / selection changes (doc unchanged) reuse the cached set. The `MutationObserver` on `<html>` re-dispatches an empty transaction on theme toggle, but since the doc reference is unchanged the cache stays correct (decorations only depend on doc content, and the `if (!dark) return null` guard handles the off case).

## Debugging save failures

- **`guest-id.ts` monkey-patches `window.fetch`.** It generates a UUID on first visit, stores it in `localStorage`, and appends it as `x-guest-id` on every `/api/` request. The Request is always constructed via `new Request()` so auto-set `Content-Type` (application/json and multipart/form-data) is preserved. Do NOT manually build a `headers` plain object, as that can suppress auto-set Content-Type — without the correct Content-Type, Express won't parse the body and returns 400.
- **Check API server logs for `content-type` and body.** A save returning 400 with `content-type: text/plain` and `body: undefined` means the JSON body was lost — the `guest-id.ts` header patch is the likely culprit.
- **The OpenAPI `DocumentUpdate` schema** must not have `minLength: 1` on `title` (only `DocumentInput` for creation needs it). Otherwise an empty title string `""` fails Zod validation and blocks the entire save including content.
- **AI chat conversations are persisted to the database.** The `POST /api/ai/chat` endpoint accepts an optional `conversationId`. When provided, user and assistant messages are saved to the `messages` table and the conversation title is auto-generated from the first user message. The frontend chat panel in `editor.tsx` includes a conversation selector, new/delete buttons, and loads message history when switching conversations.
- **After editing `openapi.yaml`**, run `pnpm --filter @workspace/api-spec run codegen` to regenerate Zod schemas and API client, then rebuild the API server (`pnpm --filter @workspace/api-server run build`).
- **Typecheck conflicts in generated code** (e.g. duplicate `ListWorldEntitiesParams`) may require trimming `api-zod/src/index.ts` — remove `export * from "./generated/types"` if it collides with `api.ts` exports.

## Debugging data loss / restoring a deleted document

- **Deleting a document in the app is a HARD delete.** `DELETE /api/documents/:id` (`documents.ts`) deletes the `documents` row and its `conversations` in one transaction. Because `chapters`, `document_versions`, and `world_entities` all have `ON DELETE CASCADE` FKs to `documents(id)`, the document's chapters, version snapshots, and world entities are deleted too — there is no soft-delete/trash. So if a user "accidentally deleted" a doc, the only recovery path is Neon's point-in-time history (see below). Do NOT tell the user it's gone until you've checked Neon.
- **Neon API base URL is `https://console.neon.tech/api/v2/` — `api.neon.tech` NO LONGER RESOLVES.** The old host returns NXDOMAIN on public DNS (CNAME and A/AAAA all NODATA). This also means `neonctl` fails out of the box (it still targets `api.neon.tech`) and the OAuth login flow is broken — use a Neon API key (`napi_...`, created at https://console.neon.tech/app/settings/api-keys) with `curl` against `console.neon.tech/api/v2/` instead. The `GET .../roles/{role}/connection_uris` endpoint is 404 in this API version — construct the restore connection string by swapping the endpoint host into the existing `DATABASE_URL` (role `neondb_owner` keeps the same password across branches). **A working Neon API key is already stored as `NEON_API_KEY` in the repo-root `.env`** (gitignored, kept for exactly this recovery workflow) — no need to re-ask the user for a key unless it stops working.
- **The Neon project is `steep-star-87166879` ("First Project")**, main branch `br-still-resonance-ap1nuv7w` (name "production"), region `aws-us-east-1`, role `neondb_owner`, DB `neondb`. **History retention is only 6 hours** (`history_retention_seconds: 21600`) — a PITR recovery must happen quickly, and it cannot recover anything deleted more than 6h ago.
- **PITR recovery recipe** (used successfully to restore a 31-chapter novel after accidental deletion):
  1. **Create a read-only branch at a timestamp before the deletion** (pick a time well inside the 6h window and before the delete; check the recovered row's `updated_at` to make sure you captured the final edits):
     `curl -X POST -H "Authorization: Bearer $NEON_API_KEY" -H "Content-Type: application/json" "https://console.neon.tech/api/v2/projects/steep-star-87166879/branches" -d '{"branch":{"parent_id":"br-still-resonance-ap1nuv7w","name":"recover-doc<id>","parent_timestamp":"<ISO-8601>"},"endpoints":[{"type":"read_only"}]}'`
     The response gives a new `branch.id` and `endpoint.host` (e.g. `ep-....c-7.us-east-1.aws.neon.tech`).
  2. **Connect to the restore branch** by reusing the password from `$DATABASE_URL` (gitignored `.env`) with the new endpoint host, then verify the deleted row is present.
  3. **Dump the rows to CSV** with `\copy (SELECT * FROM documents WHERE id=<id>) TO '...' WITH (FORMAT csv)` and likewise for `chapters`, `document_versions`, `conversations`, `messages` (match the target's column order — `SELECT *` preserves it).
  4. **Load into the main branch in one transaction** (`psql $DATABASE_URL -v ON_ERROR_STOP=1 -f restore.sql` with `BEGIN;` / `\copy ... FROM ... WITH (FORMAT csv)` / `COMMIT;`). Restore order matters for FKs: `documents` → `chapters` → `document_versions` → `conversations` → `messages`. Check for PK id collisions first (deleted row ids are usually free; the recovery branch and main share the same id sequences, so conflicts are unlikely unless other rows were created meanwhile). Always bump the sequences afterward: `SELECT setval('<table>_id_seq', GREATEST((SELECT MAX(id) FROM <table>), 1));` for each restored table.
  5. **Verify byte-identical recovery** with `md5(content)` per table compared between the restore branch and main.
  6. Keep the restore branch as a safety net until the user confirms, then delete it via `DELETE .../branches/<branch_id>`.

## When running local commands / dev servers

- **Long-running processes must run in the background.** Use `nohup ... &` or `run_in_background: true`. Verify with `curl localhost:PORT/api/healthz`.
- **Sleep a few seconds** after starting a background server before checking it. The `tmux` approach (`tmux new-session -d -s <name> '<command>'`) is more reliable in shell environments where nohup'd children get killed when the parent shell exits.
- **Stop background processes you started before declaring a task complete**, unless the user explicitly wants them left running.
- **API server needs a rebuild after source changes.** Run `pnpm --filter @workspace/api-server run build` before restarting.
- **Vite proxy config must list every API path prefix.** The `server.proxy` block in `artifacts/writer/vite.config.ts` only forwards requests matching listed prefixes (e.g. `/api/documents`, `/api/conversations`). Adding a new API route without adding its prefix to the proxy will cause silent failures (browser gets HTML instead of JSON).

## Toolbar / rich text editor troubleshooting

- **TipTap v3 StarterKit bundles many extensions internally.** `StarterKit` now includes `Underline`, `Link`, `BulletList`, `OrderedList`, `ListItem`, `Blockquote`, `Code`, `Bold`, `Italic`, `Strike`, `Heading`, `HorizontalRule`, `CodeBlock`, `Dropcursor`, `Gapcursor`, `UndoRedo`, and `HardBreak`. Individually registering them again (e.g. `import { Underline } from "@tiptap/extension-underline"` + adding to extensions array) creates duplicate registrations that silently break those features.
- **Missing transitive deps block StarterKit features in Vite builds.** `@tiptap/starter-kit` v3 depends on `@tiptap/extension-list` and `@tiptap/extensions`, which are NOT pulled in automatically by pnpm hoisting. They must be listed in `Writer-Assistant/artifacts/writer/package.json` as direct dependencies, or Vite's bundler can't resolve them and `BulletList`, `OrderedList`, `ListItem`, `Dropcursor`, `Gapcursor`, `UndoRedo` silently fail to load.
- **Font size needs the `FontSize` sub-extension.** The `setMark("textStyle", { fontSize })` approach silently drops the attribute because `TextStyle` doesn't declare `fontSize` by default. Import `FontSize` from `@tiptap/extension-text-style/font-size` and use the `setFontSize()` command instead.
- **Tailwind CSS 4 base reset strips `list-style` from all `ul`/`ol`.** ProseMirror rendered lists lose their bullets/numbers. The `.ProseMirror ul, .ProseMirror ol { list-style: revert; }` rule in the inline `<style>` block restores them. Blockquotes, `pre`, and `hr` also need explicit ProseMirror CSS because Tailwind strips browser defaults.
- **The font size dropdown must read from editor state.** Set `value={editor.getAttributes("textStyle").fontSize || ""}` so it reflects the current selection's font size. Without the `FontSize` extension this always returns empty.
- **Toolbar icon consistency.** All toolbar buttons should use Lucide icons (not emoji) for cross-platform consistency. Link → `LinkIcon`, Image URL → `ImageIcon` from lucide-react.
